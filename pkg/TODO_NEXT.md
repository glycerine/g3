## SMT relevance registration fixed in `fc3978c3c`

A real allocation-failure callback reentered the solver while the AST manager was busy. On `59b856104`, a dependency or either sign of watch returned `ErrASTPending` but replaced the outer list head. The pool held two handlers and the trail held only one entry, so popping the scope could leave the refused handler reachable. A refused mark set the relevance bit and incremented the addition count with zero owned marks and zero queued notifications. A retry then saw an already-relevant expression and skipped delivery. [Reproduction and retry tests](smtcore/smt_relevancy_registration_test.go) · [Allocation-failure fixture](smtcore/smt_quantifier_scope_failure_test.go)

Registration now acquires the source reference and records it on the trail before publishing a handler or watch. Marking acquires the reference before changing the relevance bit or notification queue. When both sources of a pair need handlers, the manager acquires both references before either link is installed. The old code left one reference and one handler behind when the second source belonged to another manager. Watch registration also validates the supplied AST before reading its assignment or children. In the ordinary build, a stale `NOT` had marked the target using its replacement’s assignment, and a stale `OR` had installed two watches on its replacement’s children. [SMT fix](smtcore/smt_relevancy.go) · [Paired reference acquisition](ast/ast_core_accessors.go) · [Reference-count tests](ast/ast_inc_ref_pair_test.go)

All eight regression cases failed against the pre-fix ordinary build and pass with the fix. The tests check retry delivery order, restoration of the outer handler, reference counts after pop and release, and correct behavior for live replacement ASTs. The ordinary `ast`, `smtcore`, and `api` package suites passed, as did the focused checked/debug/trace tests and vet for `ast` and `smtcore`. Run the focused checks from `pkg/`.

## Where to look for a larger speedup

1. **Ticket and hybrid broadcast.** Ticket’s complete verifier took 2.20× native instruction samples, hybrid 1.56×, and ARM rules 1.59×. Of 9,667 g3 Ticket samples, 4,321 passed through quantifier propagation and 3,841 through the instantiation queue. Materialization/internalization and the general rewriter overlap on these stacks. On hybrid, the first push appeared on 4,673 stacks. Put counters on both engines at the same physical batch and check. Count candidate instances, accepted instances, AST visits per materialized body, repeat visits to shared children, rewritten roots, and cycles per visit. Determine whether g3 visits more nodes or pays more for the same visit. Compare each proposed change on the complete spec with the ordinary fallback enabled. Earlier fast standalone Ticket proofs saved less when run through the whole frontend. [Holdout profiles and replay](perf/ivy_apple/holdouts/nov24-verifier-instruction-stacks.tar.xz) · [Ticket and hybrid analysis](PERF_STUDY.md#where-the-complete-ticket-and-hybrid-verifiers-spend-their-instructions)
2. **Revisit first-push preprocessing where it still dominates.** The original Apple observation was 8.61 billion excess instructions across the first pushes of ten fresh solvers. Several intervening changes altered which paths those solvers take. Use the current general-solver fallback and hybrid/TLB controls to remeasure assertion reduction, rewriting and internalization at the first physical push. Count skipped work as well as performed work. Keep exact transcript and search-counter controls. Use structurally equivalent generated cases when evaluating a proof shortcut, so applicability can be tested independently of an Apple isolate name. [First-push analysis and driver](perf/ivy_apple/holdouts/first_push_profile.py) · [Published replay findings](PERF_STUDY.md#what-remains-on-the-first-physical-push)
3. **Profile SAT propagation and conflict analysis with matched search.** On pigeon8-s1 all engines made 45,339 decisions and saw 36,007 conflicts. One measured rotation retired about 80.6 billion user instructions for the compact g3 build and 11.4 billion for Z3. This is a cleaner remaining gap than the few percent available in another iterator tweak. Capture retired-instruction profiles on this permutation and ordinary pigeon8. Bracket propagation, analysis, clause attachment/removal, temporary vectors and allocator lookups. Count watch visits, moved watches, reason walks, literals scanned and checks per event. Check cycles as well as instructions. The 8-byte lists improved wall time while increasing some instruction counts. Keep trace/extension invalidation, conflict cleanup and stale-offset tests in scope. [Go propagation](sat/sat_solver_propagation.go) · [Native SAT solver](../src/sat/sat_solver.cpp)
4. **Separate allocation rate from live heap on quantifier fingerprints.** One sampled Apple run attributed roughly 11.3 million of 86.9 million cumulative object allocations to fingerprint creation. Count attempted, duplicate, installed and retired fingerprints per batch. Test probing for an existing fingerprint before allocating variable-sized storage, and bounded solver-local reuse for common arities. Verify equal binding order, duplicate suppression, scope pop, and the results for wide outliers. Report retained capacity after popping alongside allocation rate and total verifier time. [Heap profiles and observation patch](perf/scope_restoration/worker_trials/nov25-matched-live-heap.tar.xz)

Push itself was small. Instrument registration, parent attachment, congruence insertion, reference changes and undo separately. Test whether a previously resolved child or congruence slot can serve more than one subsequent operation within the same callback-free region. Recheck identity after any callback. ## Remaining memory experiments

- **Relevance trail and handler storage.** A Go trail entry holds a full 16-byte AST handle and a one-byte kind with alignment padding, totaling 24 bytes. Native stores a pointer and kind, ordinarily 16 bytes on amd64. In the first Apple heap profile, trail growth accounted for about 5.5 MiB and link-table growth about 4.8 MiB. Census trail entries, distinct expressions, repeats per expression, live slots versus highest slot, table-head capacity and number of pooled handlers at the same Apple and Raft states. First prototype parallel slices for full handles and byte kinds. Compare a two-bit kind vector and a manager-bound compact reference stack using the existing retained-literal buffer’s ownership approach. Another candidate is a table of full handles only for distinct active keys, with short indices in the trail. Count the full cost of that directory. A refused pop can leave an unlinked entry that still owns a reference. It must remain independently releasable even after its list link has been recycled. Preserve `IncRef` validation before compressing anything. Include stale, foreign, same-slot/different-generation and callback retry cases. [Relevance implementation](smtcore/smt_relevancy.go) · [Existing compact owned storage](ast/ast_retained_literals.go)
- **SAT reasons.** The standalone SAT variable reason column still has a 32-byte row. SMT Boolean state is already 16 bytes, and its equality reason is already 8 bytes. Native SAT justifications are two words. In seven paired instruction slopes, baseline binary/mixed/clause writes plus reads took 155/165/184 instructions. A 16-byte row sharing the validated allocator owner took **139/149/169**. An 8-byte packed prototype with a full-width exceptional representation took **152/163/187**. The earlier 8-byte prototype cost 200/211/238. Combine the best 16-byte and 8-byte designs separately with the committed watch change. Measure actual heap, conflicts, cycles and end-to-end time. Verify the highest generation and kind, ordinary and foreign owners, stale offsets, overwrite, shrink/regrow and the normal-build behavior of reason accessors. Neither reason layout has shipped. [Reason benchmark](sat/sat_justification_benchmark_test.go) · [Native justification](../src/sat/sat_justification.h)
- **AST layout.** Current Go arena node slots are 100 bytes, down from 128, and canonical hash entries are 12 bytes, down from 16. At two arguments the four-manager benchmark retained 134.1 Go bytes per application. Z3 requested 52 bytes from its small allocator for that application, and the native process allocation delta measured 76.11 bytes per application. Keep those accounting boundaries visible. A 20-bit slot plus 12-bit generation with full-width escape reduced a prototype slot to 84 bytes and two-argument population to roughly 128 bytes per application. In one Apple census only six applications needed overflow under that split, versus 14,489 with 24 slot bits and eight generation bits. Whole verifier instructions generally rose. Measure occupancy, overflow locality and GC cost first if trying another packing. Preserve exact generation, traversal mark ownership and canonical probe order. [AST layout study](PERF_STUDY.md#ast-applications-and-the-memory-cost-of-traversal-marks) · [Rebuildable AST comparisons](perf/scope_restoration/worker_trials/nov24-ast-node-storage.tar.xz)
- **Keep the worker-scale controls.** Measure both fully populated and warm-after-pop fixtures, including 48×2,048 and 1,024×128. All worker state and optional caches remain solver-local. Keep forced-GC live-heap deltas, allocator capacity and sampled attribution as distinct metrics. The concrete clause directory is already 8 bytes per entry. The clause header went from 120 to 64 bytes, and the enode from 240 to 208 bytes against Z3’s 120. These are baselines for the next census. [Worker fixtures](smtcore/smt_scope_workers_benchmark_test.go) · [Clause directory evidence](perf/scope_restoration/worker_trials/nov24-concrete-clause-directory.tar.xz)
- **Lower-return variants already tried.** Unaligned expression records had the same 19.66 live bytes per dense entry as typed columns and cost more instructions. Encoding full-width variable exceptions into the flags also increased read cost. Eager or per-list watch metadata produced an 8-byte payload, but one version added roughly 17% instructions on pigeon8. A much simpler 24-byte watch remains a useful comparison if a future platform has different cache behavior. Measure actual proofs before reopening these alternatives.
