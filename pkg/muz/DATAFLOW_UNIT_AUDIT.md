# Dataflow reachability source audit

Audited `src/muz/dataflow/dataflow.cpp`, `dataflow.h` and `reachability.h` against `pkg/muz/dataflow/reachability.go` and the actual retained source consumers. The manifest labels these units ported; the live concrete analysis is covered below, not a claim that the generic template or every exceptional consumer path is implemented.

## Consumers and ownership

The only production instantiations found in `src/muz` are the two `dataflow_engine<reachability_info>` locals in `transforms/dl_mk_coi_filter.cpp`: top-down chooses rules to retain and supplies pruned-head model definitions; bottom-up tests tails, enumerates constructed unreachable facts for model definitions, and may abandon the pass on materialized facts. Go calls `TopDown`, `BottomUp`, `IsReachable` and `KnownDeclarations` from `transforms/coi.go`; its result/model ownership and exceptional cleanup are separate transform obligations. No source consumer calls dataflow `join`, `intersect`, `dump`, reader/writer `size`, or the alias independently. The `intersect` template cannot in any case instantiate for this domain, which has no `intersect` method. Do not port those unused generic interfaces.

Source engine borrows the rules, context, declarations and rule pointers; it owns its fact/worklist tables and heap vectors in the body-to-rules map, destroyed with the engine. Facts and the `dataflow.cpp` static null fact are Boolean values with no AST ownership. Go snapshots declaration handles and positive-tail counts while the finalized rule set remains open, retaining and closing each temporary rule. The set retains its own rule owner, so closing that temporary is a shared-owner decrement. The analysis owns its Go maps/slices, not declarations or AST references; consumers must keep the source manager alive when using those handles. Go requires a finalized set and returns access errors. Source works over its borrowed rule set and has no corresponding error result. `KnownDeclarations` copies its returned slice.

## Functions and branches

- `init_bottom_up` indexes every uninterpreted tail, including negative and duplicate occurrences. Each zero-positive-tail rule initializes its head; only a newly true head enters the current worklist. `BottomUp` builds the same index and seeds a Boolean once. Interpreted tails do not prevent seeding.
- `step_bottom_up` ignores a worklist symbol without indexed rules, constructs the head fact even if propagation fails, and queues a changed head for the next round. `propagate_up` returns unchanged for a true head or on the first false positive-tail fact; otherwise it marks true. Go implements these cases with map defaults and `markKnown`. The source reader maps a tail index through its declaration and defaults missing facts to false.
- `init_top_down` initializes an output only for each rule defining it; an output with no defining rules is absent. `step_top_down` copies its head fact before inserting tail facts, visits defining rules, and marks every previously false uninterpreted tail, positive or negative, for the next round. Go uses scalar facts and queue slices. The source assertion that a propagated head is reachable follows from seeding/queueing only true facts.
- Both source loops stop when the current set is empty and alternate two sets. Go uses successive slices; Boolean transitions occur once, so duplicates from repeated rules or tails do not change the result. Source hash iteration order is not insertion order; Go's deterministic discovery order is an adaptation, not a claim about source hash ordering.
- `get_fact` returns the null false fact for an absent key. Go `IsReachable` does likewise; `KnownDeclarations` separately retains fact-entry membership required by bottom-up model conversion. Source `reachability_info` constructor, `init_down`, `init_up`, `join`, `dump` and `is_reachable` respectively supply false, unconditional true, changed-on-first-true, Boolean OR, textual diagnostics and Boolean lookup. Only initialization and lookup are reached by the two consumers; generic join/dump are unused.
- Go `TopDown` additionally follows `RuleSet.Dependencies` nested under finalized interpreted or quantified tails. This deliberately conservative extension prevents pruning nested predicate definitions; it is broader than the source dataflow loop over top-level uninterpreted tails. `mk_quantifier_abstraction::mk_tail` can introduce this shape by replacing an internal array-predicate tail `P(a)` with `forall i. P′(i, select(a,i))`, wrapped as an equality with true; its head rewrite creates the corresponding `P′` definitions. Source's registered default pipeline places this pass before later cone passes, although intervening quantifier instantiation and inlining may remove the occurrence. For a surviving intermediate rule set whose `P′` definition forces it true, deleting that definition can let the quantified condition and hence an output goal become false; retaining it avoids that loss. Initial rule checks reject this nested quantified shape in several engines, but they run before preprocessing. `TestQuantifierAbstractionExpandsInternalArrayPredicate` checks the actual Go abstraction output followed by `TopDown`, and `TestConePreservesNestedQuantifiedPredicateDefinition` checks resulting rule/model retention. A public C++ query demonstrating this exact default-pipeline outcome has not been established; retain the conservative Go behavior rather than claiming source fidelity or a proven end-to-end source failure.
- Header include guards are the only preprocessor conditionals in the audited files. `TRACE` and `SASSERT` are diagnostics, not additional analysis paths. The commented fact interface describes a template contract, not an extra instantiation.

## Evidence and remaining limits

`TestReachabilityRunsFromIngestedHornProgram` covers closed-set enforcement, multi-round propagation, disconnected rules, negative-tail seed and top-down propagation, an unreachable head whose fact was constructed by a partial positive match, and an output without rules. `TestConeOfInfluencePrunesOutsideAndUnfoundedRules`, `TestConePluginCapturesOrderedModelDefinitions`, the `coi_bottom_up_source_test.go` tests and `TestConePreservesNestedQuantifiedPredicateDefinition` cover the corresponding transform consumers and their model/cleanup behavior. These checks do not prove all transform proof, model or exceptional lifecycle behavior; those remain in the transform audit. They also do not establish source hash-container iteration order, which the Go code does not reproduce.

A local C++ comparison used `z3 -v:10` (the available executable reports Z3 4.7.1) on a Spacer query with `P : (Array Bool Bool) -> Bool`, rules `P(a)` and `P(a) => Goal`, and `xform.quantify_arrays=true`. With `xform.instantiate_quantifiers` either false or true, the executable reported abstraction, a no-op quantifier-instantiation pass and no-op inliner, then a post-abstraction cone pass changing five rules to four. The query subsequently returned `unknown` with a nested-predicate rejection containing `P(i, select(a,i))`. This establishes that a nested occurrence can survive through cone in that C++ run; verbose output does not identify the rule removed by cone, and the rejected query does not establish an incorrect SAT/UNSAT result. The locally installed executable is comparison evidence, not a dependency of the Go tests. Both options default to false, so the abstraction requires explicit enabling; the quantifier-instantiation plugin is registered in source but checks its separate option before acting. The Go `TestQuantifierAbstractionExpandsInternalArrayPredicate` exercises abstraction, default-enabled inlining, and cone filtering with instantiation disabled, and verifies the abstracted definition remains reachable and retained. This selected pass sequence does not reproduce every intervening default pipeline plugin or prove the public Go query outcome.

The comparison input and command were:

```smt2
(set-option :fixedpoint.engine spacer)
(set-option :fixedpoint.xform.quantify_arrays true)
(set-option :fixedpoint.xform.instantiate_quantifiers false)
(declare-rel P ((Array Bool Bool)))
(declare-rel Goal ())
(declare-var a (Array Bool Bool))
(rule (P a))
(rule (=> (P a) Goal))
(query Goal)
```

Run `z3 -v:10 /tmp/g3-dataflow-array.smt2`; repeat with `xform.instantiate_quantifiers` set to `true` for the second comparison.
