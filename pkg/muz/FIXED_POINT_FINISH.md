# Fixedpoint port completion checklist

This tracks completion of the whole `src/muz/` port in `pkg/muz/`, including live dependencies outside that directory. A working engine or green test is not a whole-source completion claim. Source algorithms, proofs, models, incremental behavior, diagnostics and explicit ownership must all be accounted for.

Last updated: 2026-11-02. Work is active. No engine is declared fully audited by this document.

## How to follow progress

Each completed item needs source paths, implementation/test evidence and a commit in the progress log. Unchecked means incomplete or unproven. Preserve existing encodings, safeguards and test coverage. Exclude dead source only after checking live consumers. Keep commits small and frequent; use focused native tests. The user runs checked/debug tests separately. Run the full native suite sparingly, roughly hourly.

## Active delivery priorities

The user approved parallel implementation on 2026-11-02. Prioritize live solver behavior, original-rule models/proofs/witnesses, incremental updates and transformation integration over diagnostic polish. Existing diagnostic and ownership obligations remain open until verified; this ordering does not remove them or lower completion requirements.

Use three or four independent implementation lanes selected from current unchecked functional items: shared context selection/enumeration, engine and proof behavior, live Duality consumers, and registered relational plugins. Give shared files one owner and coordinate cross-lane changes through integration. Each lane delivers a small source-backed behavior change or meaningful semantic regression, with focused native tests and explicit remaining gaps. The integration owner reviews patches, updates this checklist/inventory and commits passing slices, targeting 5–10-minute checkpoints. Do not wait for every lane before committing a ready slice.

Run relevant cross-package checks at integration and the full native suite roughly hourly, avoiding duplicate active runs. The user continues checked/debug validation. Track completed behaviors and dependencies rather than translated-file counts; keep partial source statuses until the wider audit is actually complete.

Acceleration tactics are durable for every batch:

- Select work from the dependency frontier: prefer a live source consumer whose dependencies already exist, and port two or more source units together when that is the smallest coherent Go design.
- Divide lanes by non-overlapping ownership, not arbitrary file counts. Use read-only source triage before editing shared infrastructure; the integration owner alone coordinates cross-lane files, the inventory and this checklist.
- Prioritize actual registered engine/transform/relation specializations and end-to-end query paths. Do not spend a lane on dead templates, unused adapters or diagnostic polish while a functional consumer remains open.
- Give each behavior a source-derived semantic oracle, ownership/lifecycle assertions and a focused native package test. Preserve guards and existing tests; record legacy source limitations explicitly instead of inventing silent divergences.
- Integrate and commit each green slice immediately with a one-sentence message, then reassign that lane from the next unchecked dependency-frontier item. Run affected cross-package checks after integration and reserve the full native suite for the roughly hourly checkpoint.
